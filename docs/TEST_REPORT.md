## 業務驗收案例（任務書第 10 節）

`tests/integration/business-cases.test.ts`，每個案例結束後皆驗證「每批在庫量 = 帳本加總、保留量 = 有效保留加總」。

| Case | 驗證內容 | 結果 |
| --- | --- | --- |
| 1 烘焙與失重率 | 500g → 425g：生豆 −500、熟豆 +425、失重率 15%、DTR 20%、熟豆成本正確；生豆不足時回滾不產生負庫存；無事件時不計算 DTR | ✅ |
| 2 熟豆分裝 | 425g 分裝 4×100g + 損耗 3g → 剩 22g、成品 +4、包材各 −4、成本 = 403g×熟豆單價 + 包材、可追溯到烘焙批次；包材不足整筆回滾；濾掛自訂 11.5g | ✅ |
| 3 訂單保留 | 4 包庫存、兩筆並行各 3 包 → 只成功 1 筆、保留 3、不超賣；8 筆並行各 1 包 → 只成功 5 筆；相同 idempotencyKey 不重複建單 | ✅ |
| 4 重複確認付款 | 3 個並行確認 → 只有 1 筆付款紀錄、不扣庫存、不產生出貨；2 個並行出貨 → 只成功 1 次、只扣帳 1 次 | ✅ |
| 5 取消訂單 | 釋放保留、可售恢復、保留與分配紀錄保留為 RELEASED；已出貨不可取消 | ✅ |
| 6 接單後分裝 | 無 200g 現貨 → 待分裝、預留熟豆 400g；其他分裝與訂單無法使用該 400g；完成分裝後成品分配給訂單並轉可出貨；取消時生產單取消、預留釋放 | ✅ |
| 7 歷史成本 | 出貨後更正生豆單價、修改售價 → 舊訂單金額與成本快照不變；新烘焙使用新成本、新訂單使用新售價 | ✅ |
| 8 退貨 | 退回待檢批次（QUARANTINE），可售不變；超退被拒絕；檢查合格後才重新入庫；重複檢查被拒絕 | ✅ |
| 9 曲線匯入 | 合法 CSV 自動對應欄位、21 點、RoR 計算、保存 SHA-256；重複匯入拒絕；錯誤格式回報具體行號（時間未遞增、非數字、溫度超出範圍）；Artisan .alog 解析事件 | ✅ |
| 10 全流程追溯 | 訂單 → SKU → 包裝批次 → 烘焙批次 → 生豆批次一致；數量一致；成本來源一致；追溯結果不含顧客姓名、電話、地址 | ✅ |
| 帳本完整性 | DB trigger 禁止修改／刪除帳本；繞過服務層寫入負庫存被 CHECK 拒絕；手動異動沖銷後餘額回復、原交易保留、不可重複沖銷 | ✅ |

## E2E 涵蓋

- 管理員登入；26 個主要頁面與 10 個模組的詳細頁可開啟、無伺服器錯誤
- UI 流程：建立手動訂單 → 確認匯款 → 出貨 → 顯示追蹤號碼與批次追溯
- 庫存中心對帳正常
- 未登入：匯出 API 401、管理頁導向登入、Storefront API 401
- 公開 QR 履歷不需登入，且頁面不含成本或金額
- 手機（Pixel 7 尺寸）：抽屜選單、卡片式列表、無水平捲動、烘焙表單分段填寫

## 執行方式

```powershell
npm run db:local
```

```powershell
npm test
```

```powershell
npm run test:e2e
```

E2E 需先 `npm run db:seed`（會在開發資料庫新增測試訂單）。若要改用 Playwright 內建 Chromium：設定 `E2E_CHANNEL=chromium` 並執行 `npx playwright install chromium`（本次環境無法下載瀏覽器，故使用系統 Edge）。

## 已知限制

- 測試環境為本機；雲端部署後需依 DEPLOYMENT.md 的驗證清單再測一次。
- Artisan `.alog` 以依開源格式製作的樣本檔測試，尚未以實機產生的檔案驗證。
- 尚無效能／負載測試（單一管理員情境）。
- 無障礙：已做鍵盤焦點、標籤、aria、對比色（WCAG AA 目標）與減少動態，尚未以螢幕閱讀器完整人工測試。
